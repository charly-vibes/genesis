# Design: fix-envelope-hint-channel

## Context

See proposal.md — Why. Current state that shapes the approach:

- `src/envelope.rs:311-319` — `Envelope::error` sets `hints: None` and puts
  the `ErrorResult` (which owns `remediation`) into `data`.
- `src/evals/outcome.rs:52-60` — `parse_envelope` reads `value.get("hints")`
  only; `data.remediation` is never consulted.
- `src/evals/tests_e2e.rs:11-18` — the fixture is a hand-written JSON literal
  that no genesis constructor emits.
- `evallerina/src/envelope.rs:60-84` — a private reader already unions
  `/data/remediation` with the top-level channel.

## Goals / Non-Goals

**Goals:**

- One reader that resolves hint commands from every channel the fleet emits.
- Eval fixtures that are generated by the writers they claim to test.
- A written channel contract, so the next tool copies the contract instead of
  inventing a channel.

**Non-Goals:**

- Changing any envelope constructor signature or any tool's output bytes.
- Removing the top-level `hints` channel, or deprecating it on the success
  path.
- Consolidating evallerina's private reader (a cross-repo ticket).

## Decisions

**Reader-first, not writer-first.** The alternative is to make genesis write
remediation into the top-level `hints` on the error path, so the existing
reader works unchanged. Rejected: it changes the output bytes of every
genesis-based tool (wai, ddL, pretended,dont, specodelic, vampiro, whisper,
spectacular) in one release, and it leaves kaya's string-valued hints and
evallerina's dual reader still divergent. A tolerant reader fixes every
consumer at once, with zero output change. The writer-side canonicalization
is a follow-up, gated on an envelope version bump.

**Union, not replacement.** `parse_envelope` returns the union of both
channels, error channel first. Replacing one channel with the other would
either drop kaya's string hints or drop ddL/wai's `data.remediation`. The
union keeps every existing producer readable.

**Tolerant entry shapes.** A hint entry may be an object with `command` or a
bare string. Reason: kaya emits `hints` as `Vec<String>`
(`kaya/src/envelope.rs`) and ddL emits `Vec<HintEntry>`; both shapes exist in
the fleet today. Strictness would turn a shape difference into a tool-fault
classification, which is the wrong signal.

**Fixtures built by the writers.** The hint-following scenario rebuilds its
stdout with `Envelope::error` + `ErrorResult` instead of a JSON literal.
Rationale: the literal encoded the reader's assumption, so it could never
disagree with the reader — exactly the failure this change exists to remove.

**Deprecation, not removal.** The top-level error-path `hints` array is
declared deprecated on the error path (readers may accept; writers are not
required to emit). Removal is scheduled for the next envelope version bump,
which is out of scope here.

**The tolerance is defensive.** No in-fleet producer emits hints on an error
path (`Envelope::error` sets `hints: None`; wai and ddL pass hints only via
`Envelope::success`; kaya emits an empty array; sunshine has no `hints`
member). The reader tolerance therefore exists for foreign and older
producers and for the ordering rule — **not** because a fleet migration is
waiting for it. Stating this explicitly keeps the next implementer from
assuming a population that does not exist.

**Both channels survive a conflict.** When the two channels name *different*
commands, both are reported, error channel first; neither is discarded. The
alternative — "the error channel wins" — would satisfy every scenario while
silently narrowing the union the proposal promises. Consumers compare by
membership (`hint_commands.iter().any(...)` in `src/evals/checks.rs:157-165`,
`commands.iter().any(...)` in `evallerina/src/envelope.rs:113-118`), so a
union is safe for today's checks.

## Risks / Trade-offs

- [A producer emits a channel nobody reads] → Mitigation: the union makes
  extra channels harmless; the deprecation is documented, not enforced.
- [Tolerance hides a real writer bug (a tool emits `hints` on the error path
  where it should emit remediation)] → Mitigation: the conformance kit
  (separate change `add-envelope-conformance-kit`) asserts the *writer* shape
  separately from the reader's tolerance.
- [evallerina keeps its own reader and drifts again] → Mitigation: a
  cross-repo ticket consolidates it onto `genesis::evals::parse_envelope`.
- [The union changes existing eval reports] → Mitigation: scenarios that
  previously reported "hint-blind" against a `data.remediation` producer now
  pass. That is the intended correction; the affected evallerina recordings
  are re-run in the evallerina repo — and the genesis-side recorded corpus
  (`evallerina/src/recorded.rs`, `scenarios/*.json`) is re-run in the same
  ticket, with every classification flip reviewed rather than absorbed.
- [A union entry changes a check that expects exactly one hint] → Mitigation:
  today's checks compare by membership, so a union is safe; the spec states
  the conflict rule (both survive) so a future equality-style check has a
  stated contract to follow.

## Migration Plan

1. Land the tolerant reader and the genesis-built fixtures together (one
   release) — a reader-only change is safe to ship alone.
2. Announce the channel contract in the `envelope` spec and the CHANGELOG.
3. Cross-repo: evallerina delegates its reader to `genesis::evals` (separate
   ticket); no other tool changes.
4. Rollback: revert the reader; no data or state is involved.

## Open Questions

- Whether the top-level error-path `hints` channel is removed in envelope
  version `0.2`, and whether that bump is worth a fleet-wide migration —
  deferred; it changes no behavior in this change.
