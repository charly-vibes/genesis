# Design: populate-tool-registry

## Context

See proposal.md — Why. State that shapes the approach:

- `src/discovery.rs` already scans a `.genesis/tools.toml` manifest and
  supports `file` and `directory` detectors; the manifest in this repo has two
  entries (`testaruda` — file marker `testaruda.toml`; `wai` — directory
  marker `.wai`).
- The fleet scan during the audit found 18 Rust CLIs: wai, dont,
  dulce-de-leche, testeruda, espectacular, pretender, specodelic, whisper,
  vampiro, podras, evallerina, bajan, sad, gently, kaya, wild, sunshine,
  funkalization (plus `fotos`, a GUI app, and genesis itself). `testaruda`'s
  source tree was unreadable during the audit, so its detector is still
  unverified.
- Beads `genesis-lu6` tracks registering the `.espectacular` detector.

## Goals / Non-Goals

**Goals:**

- A registry that answers "which tools does the suite have" and "which are
  installed here" as two different questions.
- Every fleet CLI represented, with a description and a detector.
- Detection that never makes a caller's command fail.

**Non-Goals:**

- Installing, upgrading, or removing tools (ddL's job).
- A registry service or a remote registry.
- Detecting a tool's *version* (the registry records presence, not versions).

## Decisions

**Declared vs. installed are separate fields.** The alternative is one boolean
"present". Rejected: the fleet registry's purpose is to know what exists; a
tool's absence in one working copy is not evidence the tool does not exist.
Two fields let a dashboard say "the fleet has 18 tools, 14 installed here".

**A `command` detector joins `file` and `directory`.** Some tools ship no
marker file in a consumer's repo (wai ships `.wai/`, testeruda ships
`testaruda.toml`, but e.g. a tool that only installs a binary does not).
Without a `command` detector, such tools are undetectable outside their own
repo. Rationale: `PATH` lookup is the same mechanism an installer uses.

**A registry entry without a detector is invalid.** Rationale: an entry that
cannot be detected cannot answer "installed", so it is a manifest error, not
a silent entry. Validation is reported, not fatal.

**Absence is never an error.** A discovery call is used by status dashboards,
doctor checks, and setup wizards — all of which want a list, not a failure.
Rationale: making absence an error would force every caller into a
`Result`-flattening dance for a normal state.

**The fleet reference copy lives here; each tool declares its own entry.**
Two copies of the same fact drift. Resolution: the tool's own repo owns its
entry (that repo's `.genesis/tools.toml`), and this repo's manifest is the
fleet-wide reference used by fleet-level tooling. The reference copy is
regenerated, not hand-maintained — a task states so.

**`testaruda` waits for a re-scan.** Its detector is not guessed. The entry
is added with a verified detector once the repo is readable; until then it
keeps its current file-marker entry.

## Risks / Trade-offs

- [The reference copy drifts from the per-tool declarations] → Mitigation:
  the reference copy is regenerated by a task that reads each tool's own
  manifest; a drift check compares them.
- [A `command` detector reports a tool installed because an unrelated binary
  has the same name] → Mitigation: the command name is the tool's own
  binary name; the check records which path resolved.
- [Registry growth slows discovery] → Mitigation: the manifest is a handful
  of entries per tool; detection is a filesystem/`PATH` probe each.

## Migration Plan

1. Land the schema change (declared/installed, `command` detector, invalid
   entry reporting) — additive.
2. Populate the reference manifest in this repo (one task per tool entry).
3. Each tool repo declares its own entry (one ticket per repo).
4. Rollback: the manifest can be emptied; the schema change is additive.

## Open Questions

- Whether the reference copy should be generated by a script that clones each
  tool's manifest, or maintained by hand with a drift check — deferred; it
  changes no behavior, and the drift check is a task either way.
